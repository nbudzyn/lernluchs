- C (falsch): proposal.md. Erklärung: proposal.md beschreibt Zweck und Umfang, nicht die abhakbaren Tasks. Quelle: https://openspec.dev/docs/schemas/spec-driven

## S06: Was ist die Standardreihenfolge beim Entwurf der Artefakte?
- A (richtig): Proposal, dann Specs und Design, danach Tasks. Erklärung: Das Proposal steht zuerst, Tasks folgen auf Specs und Design. Quelle: https://openspec.dev/docs/schemas/spec-driven
- B (falsch): Tasks, dann Code, danach Proposal. Erklärung: Tasks setzen im Standardablauf Proposal, Specs und Design voraus und stehen nicht am Anfang. Quelle: https://openspec.dev/docs/schemas/spec-driven
- C (falsch): Design erst nach dem Archivieren. Erklärung: Design wird vor Apply entworfen, sofern es für die Änderung nötig ist. Quelle: https://openspec.dev/docs/schemas/spec-driven

## S07: In welcher Reihenfolge können Specs und Design nach dem Proposal entstehen?
- A (richtig): In beliebiger Reihenfolge vor Tasks. Erklärung: Beide folgen dem Proposal und gehen Tasks voraus. Quelle: https://openspec.dev/docs/schemas/spec-driven
- B (falsch): Nur Design vor Specs. Erklärung: Das Schema erlaubt Specs und Design in beiden Reihenfolgen. Quelle: https://openspec.dev/docs/schemas/spec-driven
- C (falsch): Erst nach dem Apply-Schritt. Erklärung: Beide Artefakte werden vor Apply und Tasks entworfen. Quelle: https://openspec.dev/docs/schemas/spec-driven

## S08: Wann kann design.md im Standardschema entfallen?
- A (richtig): Wenn keine seiner Bedingungen zutrifft. Erklärung: OpenSpec lässt Design bei unnötigem Bedarf aus. Quelle: https://openspec.dev/docs/schemas/spec-driven
- B (falsch): Immer bei neuen Abhängigkeiten. Erklärung: Neue Abhängigkeiten sind ein möglicher Grund für ein Design, nicht für sein pauschales Weglassen. Quelle: https://openspec.dev/docs/schemas/spec-driven
- C (falsch): Immer bei Architekturänderungen. Erklärung: Architekturänderungen können ein Design erforderlich machen. Quelle: https://openspec.dev/docs/schemas/spec-driven

## S09: Unter welcher Bedingung dürfen Specs im Schema ausgelassen werden?
- A (richtig): Wenn skip_specs ausdrücklich gesetzt wird. Erklärung: Die Schema-Dokumentation nennt skip_specs. Quelle: https://openspec.dev/docs/schemas/spec-driven
- B (falsch): Sobald Tests existieren. Erklärung: Vorhandene Tests setzen die Spec-Pflicht nicht automatisch außer Kraft. Quelle: https://openspec.dev/docs/schemas/spec-driven
- C (falsch): Sobald der Prompt kurz ist. Erklärung: Die Kürze eines Prompts ist kein skip_specs-Kriterium. Quelle: https://openspec.dev/docs/schemas/spec-driven

## S10: Wo liegt eine Delta-Spec für eine neue Capability?
- A (richtig): specs/<capability-path>/spec.md im Änderungsordner. Erklärung: Das Standardschema nutzt einen Pfad je Capability. Quelle: https://openspec.dev/docs/schemas/spec-driven
- B (falsch): Direkt in package.json. Erklärung: package.json ist keine Ablage für Delta-Anforderungen einer Capability. Quelle: https://openspec.dev/docs/schemas/spec-driven
- C (falsch): Ausschließlich im Chatprotokoll. Erklärung: Nur im Chat gehaltene Anforderungen sind nicht das dokumentierte Spec-Artefakt. Quelle: https://openspec.dev/docs/schemas/spec-driven

## S11: Was sollen Specs primär beschreiben?
- A (richtig): Was Nutzer oder andere Systeme beobachten können. Erklärung: Die Spec ist ein Verhaltensvertrag. Quelle: https://openspec.dev/docs/schemas/spec-driven
- B (falsch): Interne Klassennamen als Pflicht. Erklärung: Interne Klassennamen können sich ohne Verhaltensänderung ändern und gehören eher ins Design. Quelle: https://openspec.dev/docs/schemas/spec-driven
- C (falsch): Eine genaue Schrittfolge der Implementierung. Erklärung: Eine Schrittfolge beschreibt das Wie und gehört in Tasks oder Design. Quelle: https://openspec.dev/docs/schemas/spec-driven

## S12: Welche Angabe gehört zu einem guten Spec-Szenario?
- A (richtig): Eingabe beziehungsweise Bedingung und erwartetes Ergebnis. Erklärung: OpenSpec betont prüfbare Szenarien mit WHEN und THEN. Quelle: https://openspec.dev/docs/schemas/spec-driven
- B (falsch): Nur der Name einer Bibliothek. Erklärung: Eine Bibliothek benennt keine beobachtbare Bedingung und kein erwartetes Ergebnis. Quelle: https://openspec.dev/docs/schemas/spec-driven
- C (falsch): Nur die geschätzte Arbeitszeit. Erklärung: Die Arbeitszeit ist keine WHEN/THEN-Aussage über Systemverhalten. Quelle: https://openspec.dev/docs/schemas/spec-driven

## S13: Welcher Inhalt gehört eher ins Design als in eine Spec?
- A (richtig): Die Wahl einer Bibliothek oder internen Struktur. Erklärung: Designs erklären technische Entscheidungen. Quelle: https://openspec.dev/docs/schemas/spec-driven
- B (falsch): Das sichtbare Ergebnis bei fehlerhafter Eingabe. Erklärung: Ein sichtbares Fehlerergebnis ist Teil des Verhaltensvertrags und gehört in die Spec. Quelle: https://openspec.dev/docs/schemas/spec-driven
- C (falsch): Eine externe Sicherheitsgrenze. Erklärung: Eine externe Sicherheitsgrenze betrifft beobachtbare Anforderungen und kann Spec-Inhalt sein. Quelle: https://openspec.dev/docs/schemas/spec-driven

## S14: Was sollte eine Spec bei Fehlerfällen festhalten?
- A (richtig): Das beobachtbare Verhalten im Fehlerfall. Erklärung: OpenSpec nennt Fehlerbedingungen als Spec-Inhalt. Quelle: https://openspec.dev/docs/schemas/spec-driven
- B (falsch): Nur den internen Stacktrace. Erklärung: Ein interner Stacktrace ist keine geeignete verlässliche Beschreibung des Nutzerverhaltens. Quelle: https://openspec.dev/docs/schemas/spec-driven
- C (falsch): Nur die Zahl der Codezeilen. Erklärung: Die Codezeilenzahl beschreibt kein Ergebnis im Fehlerfall. Quelle: https://openspec.dev/docs/schemas/spec-driven

## S15: Was bedeutet ein Delta-Abschnitt ADDED Requirements?
- A (richtig): Neue Anforderungen einer Capability. Erklärung: ADDED kennzeichnet hinzugefügtes Verhalten. Quelle: https://openspec.dev/docs/schemas/spec-driven
- B (falsch): Eine bloße Umbenennung ohne Änderung. Erklärung: Eine reine Umbenennung verwendet RENAMED statt ADDED. Quelle: https://openspec.dev/docs/schemas/spec-driven
- C (falsch): Das Löschen alter Tests. Erklärung: Das Löschen von Tests ist keine neue fachliche Anforderung. Quelle: https://openspec.dev/docs/schemas/spec-driven

## S16: Was erfordert ein MODIFIED-Abschnitt für eine bestehende Anforderung?
- A (richtig): Den vollständigen aktualisierten Anforderungsblock. Erklärung: OpenSpec warnt vor Teilblöcken bei MODIFIED. Quelle: https://openspec.dev/docs/schemas/spec-driven
- B (falsch): Nur die geänderte Textzeile. Erklärung: Nur eine geänderte Zeile kann übrige Szenarien beim Archivieren verlieren. Quelle: https://openspec.dev/docs/schemas/spec-driven
- C (falsch): Ausschließlich eine neue Überschrift. Erklärung: Eine neue Überschrift allein enthält keinen vollständigen Anforderungsblock. Quelle: https://openspec.dev/docs/schemas/spec-driven

## S17: Was muss eine entfernte Anforderung im Delta begründen?
- A (richtig): Grund und Migration. Erklärung: REMOVED fordert Reason und Migration. Quelle: https://openspec.dev/docs/schemas/spec-driven
- B (falsch): Nur eine neue Versionsnummer. Erklärung: Eine Versionsnummer erklärt nicht, warum eine Anforderung entfällt und wie migriert wird. Quelle: https://openspec.dev/docs/schemas/spec-driven
- C (falsch): Nur den Namen des Autors. Erklärung: Ein Autorenname ersetzt weder Grund noch Migrationshinweis. Quelle: https://openspec.dev/docs/schemas/spec-driven

## S18: Was unterscheidet RENAMED von MODIFIED?
- A (richtig): RENAMED ändert nur den Namen. Erklärung: Die Delta-Operation RENAMED ist für reine Namen. Quelle: https://openspec.dev/docs/schemas/spec-driven
- B (falsch): RENAMED ersetzt alle Verhaltensregeln. Erklärung: Eine Verhaltensänderung gehört unter MODIFIED und ist keine reine Umbenennung. Quelle: https://openspec.dev/docs/schemas/spec-driven
- C (falsch): RENAMED startet automatisch die Tests. Erklärung: RENAMED ist eine Delta-Markierung und kein Teststartbefehl. Quelle: https://openspec.dev/docs/schemas/spec-driven

## S19: Wie wird in OpenSpec ein Szenario als Überschrift markiert?
- A (richtig): Mit vier Markdown-Hashes. Erklärung: Die Schema-Anleitung verlangt #### für Szenarien. Quelle: https://openspec.dev/docs/schemas/spec-driven
- B (falsch): Mit einem einzigen Hash. Erklärung: Ein einzelnes Hash markiert eine Hauptüberschrift, nicht die geforderte Szenarioebene. Quelle: https://openspec.dev/docs/schemas/spec-driven
- C (falsch): Nur mit einem Bullet. Erklärung: Ein Bullet ist keine Szenarioüberschrift im verlangten Format. Quelle: https://openspec.dev/docs/schemas/spec-driven

## S20: Wann beginnt Apply im Standardschema?
- A (richtig): Wenn tasks.md mit mindestens einem Task vorliegt. Erklärung: Apply benötigt die Taskliste. Quelle: https://openspec.dev/docs/schemas/spec-driven
- B (falsch): Schon vor dem Proposal. Erklärung: Apply setzt die Taskliste voraus und startet nicht vor dem Proposal. Quelle: https://openspec.dev/docs/schemas/spec-driven
- C (falsch): Erst nach dem Archiv. Erklärung: Das Archivieren folgt der Umsetzung, es löst Apply nicht aus. Quelle: https://openspec.dev/docs/schemas/spec-driven

## S21: Wie verfolgt Apply die Umsetzung?
- A (richtig): Über Checkboxen in tasks.md. Erklärung: Das Schema verfolgt markierte Tasks. Quelle: https://openspec.dev/docs/schemas/spec-driven
- B (falsch): Über private Chats. Erklärung: Private Chats sind nicht das im Schema angegebene Tracking-Artefakt. Quelle: https://openspec.dev/docs/schemas/spec-driven
- C (falsch): Über die Zahl der Pull-Request-Kommentare. Erklärung: Die Kommentarzahl eines PR zeigt keinen abgehakten Task an. Quelle: https://openspec.dev/docs/schemas/spec-driven

## S22: Was soll ein einzelner Task laut Schema enthalten?
- A (richtig): Einen konkreten Nachweis der Fertigstellung. Erklärung: OpenSpec fordert für Tasks einen Verifikationsweg. Quelle: https://openspec.dev/docs/schemas/spec-driven
- B (falsch): Nur ein loses Stichwort. Erklärung: Ein Stichwort ohne Nachweis lässt die Fertigstellung unklar. Quelle: https://openspec.dev/docs/schemas/spec-driven
- C (falsch): Eine unbefristete Sammelaufgabe. Erklärung: Eine unbegrenzte Sammelaufgabe widerspricht kleinen verifizierbaren Tasks. Quelle: https://openspec.dev/docs/schemas/spec-driven

## S23: Was passiert beim Archivieren mit Delta-Anforderungen?
- A (richtig): Sie werden in die dauerhaften Specs übernommen. Erklärung: Der Quickstart beschreibt die Übernahme in Haupt-Specs. Quelle: https://openspec.dev/docs/quickstart
- B (falsch): Sie werden ohne Übernahme gelöscht. Erklärung: Archivieren führt Delta-Anforderungen in Haupt-Specs über, es verwirft sie nicht. Quelle: https://openspec.dev/docs/quickstart
- C (falsch): Sie werden in den Lockfile verschoben. Erklärung: Ein npm-Lockfile ist kein Ziel für fachliche Anforderungen. Quelle: https://openspec.dev/docs/quickstart

## S24: Was passiert beim Archivieren mit dem Änderungsordner?
- A (richtig): Er wird ins Archiv verschoben. Erklärung: Der Quickstart zeigt den Archivschritt. Quelle: https://openspec.dev/docs/quickstart
- B (falsch): Er bleibt als aktiver Ordner stehen. Erklärung: Der aktive Änderungsordner wird beim Archivieren verschoben. Quelle: https://openspec.dev/docs/quickstart
- C (falsch): Er wird in Quellcode umgewandelt. Erklärung: Der Ordner wird nicht in ausführbaren Quellcode umgewandelt. Quelle: https://openspec.dev/docs/quickstart

## S25: Wie ist OpenSpec im Verhältnis zu Git zu verstehen?
- A (richtig): Der Änderungsablauf ist von Git-Commits getrennt. Erklärung: Der Quickstart nennt Git als getrenntes Anliegen. Quelle: https://openspec.dev/docs/quickstart
- B (falsch): Es ersetzt Git vollständig. Erklärung: OpenSpec organisiert Änderungsartefakte, ersetzt aber nicht Git als Versionsverwaltung. Quelle: https://openspec.dev/docs/quickstart
- C (falsch): Es verhindert jeden Commit. Erklärung: Der Quickstart beschreibt Commits weiterhin als getrennten Teil des Workflows. Quelle: https://openspec.dev/docs/quickstart
